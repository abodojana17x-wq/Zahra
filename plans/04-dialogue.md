## 1. الفكرة المحورية

خطة المنافس (المرحلة 4): «حالة المحادثة: آخر كيان، slots، حل إحالات بسيطة، أسئلة توضيح، ذاكرة مستخدم محلية مع زر مسح، تركيب الرد من بلوكات. حاليًا `lastTopic` بيتستخدم كجملة «بالمناسبة» عشوائية بنسبة 20%؛ ده لازم يبقى سياق حقيقي.»

زهرة أغنى (3 مستويات ذاكرة + ملف شخصي + مزاج + شخصية)، لكن **الغنى خطر**: أي خلل في الربط بينهم ينتج ردًا يبدو ذكيًا ويكون مخترعًا. لذلك هذه المرحلة تُعرّف **مصدرًا واحدًا للحالة**:

```
DialogueState(
  turns: List<ConversationTurn>,      // الحقيقة الوحيدة
  lastEntity: Entity?, lastRoute: Route?, lastUnitId: String?,
  slots: Map<Slot, SlotValue>,        // city, date, currency, unit, topic, person
  pendingClarification: Clarification?, userProfile: UserProfile, mood: MoodResult
)
```

**قاعدة لا تُكسر:** لا يجوز لأي قالب ذاكرة أن يُستخدم إذا كانت `turns` لا تحتوي المرجع المذكور. الاختبار يفحص النص الناتج بحثًا عن أنماط «كما ذكرت/ما زال/قلت لي/حديثك السابق/بالمناسبة» ويقارنها بسجل الدورات.

## 2. مسارات العمل

### المسار A — توحيد حالة المحادثة (`dialogue/DialogueState.kt`)

1. ادمج المصادر الأربعة (`UnifiedMemoryManager`, `TopicMemory`, `ContextManager`, `ContextAndCorrectionTracker`) خلف واجهة واحدة؛ امنع أي محرك من قراءة `lastTopic` مباشرة.
2. `Slot` enum: `CITY, DATE, TIME, CURRENCY, UNIT, TOPIC, PERSON, LANGUAGE, CODE_LANG`. لكل slot: قيمة، ثقة، مصدر (من المستخدم/مستنتج/افتراضي)، ووقت انتهاء صلاحية.
3. **انتهاء الصلاحية:** `DATE` ينتهي بعد دورة أو تبديل موضوع؛ `CITY` يبقى حتى يغيّره المستخدم؛ `TOPIC` يبقى 3 دورات كحد أقصى. كل قاعدة موثقة ومختبرة.
4. `clearConversation()` + زر **«مسح الذاكرة»** في `SettingsScreen.kt` يعرض عدد العناصر المحذوفة ويطلب تأكيدًا — نفس مبدأ خصوصية المنافس لكن بشفافية أكبر.

### المسار B — حل الإحالات (`dialogue/ReferenceResolver.kt`)

1. أنماط إلزامية من المجموعة: «وإيه عاصمتها؟» (إحالة لمدينة), «وبكرة؟» (إحالة لتاريخ/طقس), «طب بالجنيه؟» (slot عملة), «عنه/عنها/عنهم», «كمان», «نفس السؤال بس…», «طب وإيه حلّه؟».
2. إذا `lastEntity == null` → **لا تُخمّن**: اسأل توضيح «تقصد إيه بالـ «ها»؟» مع أقرب 2 كيانات من آخر 3 دورات.
3. اختبارات: 20 سيناريو متعدد الدورات (turn 1 → turn 2 → turn 3) مع تدوير عشوائي للردود (8 تكرارات).

### المسار C — أسئلة التوضيح (`dialogue/ClarificationPolicy.kt`)

1. إذا `slot` مطلوب وناقص: سؤال واحد مختصر + خياران (مثل «الطقس فين؟ القاهرة ولا إسكندرية؟»).
2. **حد أقصى سؤال توضيح واحد متتالي**؛ بعده إمّا أفضل إجابة ممكنة أو امتناع صريح — حتى لا يتحول المساعد لـ «أسئلة بلا إجابات».
3. التوضيح يُسجّل كـ `pendingClarification` ويُستهلك في الدورة التالية بغض النظر عن صياغة المستخدم.

### المسار D — إصلاح المشاعر (6 حالات فاشلة + منع التعميم)

1. لكل حالة من تقرير المنافس (`مش قادر اذاكر`, `حاسس اني وحيد`, `اتخانقت مع صاحبي`, `انا فرحان النهارده`, `انا زهقان`, `هل تحبني`) اكتب اختبارًا يحدد **المزاج الصحيح** والنية الصحيحة، ثم ردًا محددًا لا «حكمة عامة عشوائية».
2. ارسم مصفوفة `MoodAnalyzer` الحالية (كلمات → مزاج) وابحث عن التداخل: «وحيد» shouldn't → ملل. أضف كلمات دالة مع أوزان واضحة + حالات نفي («مش حاسس اني وحيد»).
3. **قاعدة المحتوى قبل الأسلوب:** `MoodAdaptiveResponseBuilder` يضيف طبقة تعاطف/نبرة فقط، ولا يستبدل جوهر الرد. أي رد عاطفي لازم يجيب عن الجملة نفسها (مثلاً «مش قادر اذاكر» → خطوة عملية صغيرة + تعاطف، مش دراسة عن الرضا).
4. اختبار يمنع أي رد من احتواء > 40% نص عام غير مرتبط بكلمات المستخدم (مقياس بسيط: تداخل lexical + وجود كيان من السؤال).

### المسار E — تركيب الرد من بلوكات (`dialogue/ResponseComposer.kt`)

```
[افتتاحية قصيرة] + [جوهر: رقم/تعريف/مصدر/كود] + [متابعة: سؤال أو خطوة تالية]
```

1. كل بلوك له مصدر (`TOOL | RETRIEVAL | MEMORY | CLARIFICATION | ABSTAIN`) ويُسجّل في `traceId`.
2. `PersonalityManager` و`StyleApplier` يعملان **بعد** اكتمال الجوهر، ولا يغيران الأرقام أو الروابط أو أوامر الامتناع (D8).
3. `ResponseValidator` يتحقق أخيرًا: لا تناقض، لا تكرار، لا ذاكرة متخيّلة، لا وعود طبية/دينية بلا مصدر.
4. `GreetingVariator` مسموح بالتنويع في الافتتاحية فقط، بشرط ألا يكرر اسم المستخدم أكثر من مرة في الرسالة الواحدة.

أُضيفت المهام التالية بعد البحث والمراجعة؛ هذا توثيق بأثر رجعي، وليس ادعاءً بأن قائمة الخطة عُدّلت قبل بدء الكود:

- [x] ربط دخول الراوتر بمعرّف الجلسة ومسح السياق المؤقت عند تبديلها، لمنع انتقال عمل قديم إلى سياق جديد.
- [x] تقييد استخراج الأسماء بالنص الإيجابي الصريح، واختبار النفي وتصحيح الاسم وحذف إحالات الترحيب غير المثبتة.
- [x] منع الإقرار بتراجع غير منفذ وإظهار فشل حفظ التصحيح بدل تأكيده؛ لا يوجد تنفيذ للتراجع نفسه.
- [x] حماية أمر التذكير من التحويل لطقس، ورفض توقعات طقس مستقبلية بدل تقديم الطقس الحالي على أنه توقع.
- [x] حفظ الكتل والـtrace مع الرسالة، وإضافة حاجز محافظ لادعاءات الذاكرة وبعض التناقضات والمحتوى غير المسند.
- [x] حفظ نسخة مشفرة والتحقق منها قبل إزالة النسخة القديمة، واستكمال الترحيل المنقطع بعد فك مصادق عليه، مع عرض نطاق المسح والفشل الجزئي.
- [x] إضافة استجابة محلية محافظة لحالات إيذاء النفس الصريحة، واختبار معجمي محدود لخصوصية ردود المشاعر.
- [x] إضافة اختبارات للغموض والتوضيح والنفي والجلسات والتخزين والمزاج والأسلوب، دون تعديل ملف التقييم المجمد؛ تشغيل الفحوص المعزولة فقط موثق في سجل المرحلة.
- [x] توحيد مستهلكي السياق القديم خلف `DialogueHistorySource` (إسقاط للقراءة فقط من `DialogueState`)، مع مفتاح رجوع آمن `LegacyContextMode.MIRRORED` واختبار تكافؤ (`DialogueContextUnificationTest` + `DialogueContextEquivalence`) — D29. **حد:** النسخ التوافقية ما زالت قابلة للاستدعاء منفردة، و`ResponseBuilder` غير مسنَد في الموجّه، ولا تُعاد الجلسات السابقة من الأرشيف.
- [x] توسيع صيغ الإحالة/المتابعة (نفس السؤال بس…، نفس المدينة، حلّه/حلها، أي تحويل عملة، بعد بكرة، كمان مع مرجع وحيد) وتطبيق حد التوضيح على كل المسارات القديمة عبر `ClarificationBudget` — **حد:** لا تُغطّى كل صيغ العربية/اللهجات، والمصنّف النمطي قد يخطئ.
- [x] تحسين معالجة الذاكرة المعطوبة في الواجهة: `UnifiedMemoryManager.LoadIssue` + `ZahraRouter.memoryHealth()` + تحذير في `SettingsScreen`، وتفصيل عناصر الفشل الجزئي في المسح — D30.
- [x] توسيع التحقق النهائي: فحص عدم تغيّر الأرقام/الروابط/الامتناع بعد الأسلوب (`integrityProblem`)، ضمانات ونِسب غير مسندة، تناقضات صريحة، وتكرار الجمل القصيرة — مع اختبارات (`DialogueFinalSafetyTest`). **حد:** فحص نمطي لا تحقق دلالي شامل.
- [ ] التحقق من ترحيل التشفير والمسح والفشل الجزئي وسلوك مفتاح AndroidKeyStore وتكامل الجلسات على Android/Robolectric/جهاز. الاختبارات مكتوبة (`MemoryCorruptionReportingTest`، `DialogueIntegrationTest`) ولكنها **لم تُشغَّل** هنا لغياب Android SDK؛ قائمة التحقق اليدوية في `evidence/phase-04/device-checklist.md`.

استُبعدت إضافة CAMeL Tools أو Mem0 كتبعيات بسبب عدم إثبات ملاءمة حزمة Python/المعالجة السحابية للعميل المحلي على Kotlin و`minSdk 24`؛ راجع `evidence/phase-04/research.md` وD28. لم تُستبدل بذلك مجموعة التقييم ولم يُدَّعَ تكافؤ دلالي عام.
